# Релизный гейт (аудит G1 + G2)

Что проверяется перед выпуском, как это применить и как откатить.
Код изменён локально. На production ничего не применялось, ни один workflow
на GitHub не запускался.

## 1. Что было сломано

**G1 / BUG-01.** `deploy.sh` собирал и запускал контейнеры одной командой
`up -d --build || UP_RC=$?`. Ненулевой код сборки только печатал предупреждение.
Дальше шли health-проверки, на которые исправно отвечал предыдущий релиз,
и скрипт завершался нулём. Оператор видел зелёный деплой без новой версии.

Попутно: исчерпанный бюджет ожидания API не считался провалом, а недоступность
web была предупреждением.

**G1 acceptance.** Первая версия исправления сверяла версию через
`printenv DRINKX_GIT_SHA` внутри контейнера. Это не доказательство: `ENV` образа
переопределяется при запуске, поэтому старый образ, поднятый с переменной нового
релиза, проходил проверку.

**G2 / DEBT-02.** Деплой висел на собственном событии push и ни от чего не
зависел. Проверки API и web жили в отдельных workflow со своими path-фильтрами,
так что правка в `infra/`, в workflow или в корневом lockfile уезжала в прод,
не будучи проверенной ничем.

**G2 / DEBT-03.** Тестовые фикстуры строят схему через `metadata.create_all`,
а прод поднимается через `alembic upgrade head`. Два разных пути, покрыт был
один. Новая проверка миграций сразу нашла настоящий дефект — см. раздел 5.

## 2. Чем доказывается версия

`GIT_SHA` приходит build-аргументом и попадает в образ двумя способами:

| Место | Для чего | Можно ли подделать в рантайме |
|---|---|---|
| `ENV DRINKX_GIT_SHA` | удобство внутри приложения, поле `sha` в `/health` | **да**, через `docker run -e` |
| `LABEL org.opencontainers.image.revision` | решение гейта | нет, метка принадлежит образу |

Поэтому гейт читает **метку образа**, а не окружение контейнера. Порядок такой:

0. образ сервиса определяется по ключу в разобранной конфигурации Compose
   (`config --format json`). Не по строке из `config --images`: та команда
   печатает образы сервиса **вместе с зависимостями**, поэтому для api первой
   идёт строка postgres, а для web — образ api. Позиционный выбор отклонял
   исправные выпуски (замечание ревью R2);
1. после сборки запоминаются ID собранных образов и проверяется, что их метки
   называют нужный коммит;
2. после запуска для каждого из четырёх сервисов берётся ID образа, с которого
   реально поднят контейнер, и сверяется с запомненным;
3. из образа по этому ID читается метка и сверяется с `DEPLOY_SHA`.

`/health` и `/version` отдают `sha` и остаются проверкой того, что API
действительно обслуживает запросы. Они **не** заменяют проверку образов:
поле берётся из окружения, а его можно подменить.

Последняя строка скрипта всегда одна из трёх:

| Строка | Значение |
|---|---|
| `DEPLOY_RESULT=success` | все четыре контейнера подняты с образов этой сборки |
| `DEPLOY_RESULT=unverified` | запуск вручную без `DEPLOY_SHA`, сверять не с чем |
| `DEPLOY_RESULT=failed` | сборка, запуск, health или идентичность не прошли |

**Что метка доказывает и чего не доказывала.** Совпадение метки говорит
«собрано с таким `GIT_SHA`», а не «собрано ровно из этого дерева». До G4 второе
не выполнялось — см. раздел 2а.

## 2а. Чистота build context (G4 / DEBT-01)

**Что было сломано.** Код уезжал на сервер через `rsync` без `--delete` в один
и тот же каталог `/opt/drinkx-crm`. `--delete` там и нельзя было включить:
рядом лежит `infra/production/.env` с боевыми секретами, которых нет в git.
Значит, файл, удалённый из репозитория, оставался на диске сервера. А
`apps/api/Dockerfile` копирует каталоги целиком:

```
COPY apps/api/app ./app
COPY apps/api/scripts ./scripts
COPY docs ./docs
```

Удалённый модуль попадал в образ. Метка ревизии этого не ловит: она про то, с
каким `GIT_SHA` запускали сборку, а не про то, что лежало в контексте.

Воспроизведение: `infra/production/tests/repro_build_context_debt01.py` —
временный git-репозиторий, релиз A с файлом, релиз B без него, настоящий
`rsync` в каталог-заглушку. Файл переживает релиз B. Шаг «попал ли он в образ»
там **НЕ ВЫПОЛНЯЛСЯ**: демона Docker в среде разработки нет, вывод сделан по
содержимому Dockerfile.

**Как исправлено.** Единица доставки — не синхронизация рабочего каталога, а
архив коммита.

| Шаг | Что делает |
|---|---|
| `make_release_archive.sh <sha> <out>` | в CI: `git archive` этого коммита, сверка списка файлов с `git ls-tree`, отказ при секретах, `sha256` рядом |
| `scp` | архив уезжает в `/opt/drinkx-crm/incoming/` |
| `remote_prepare_release.sh` | на сервере через `bash -s` (в репозитории, а не на диске сервера): проверка суммы, распаковка в приватный каталог, проверки, переименование в `releases/<sha>`, чистка старых. Если `releases/<sha>` уже собран из этого же архива — каталог переиспользуется, ничего не удаляется |
| `deploy.sh` | отказывается считать выпуск проверенным, если работает не из `<root>/releases/<DEPLOY_SHA>` |

`git archive` физически не может отдать ни untracked-файл, ни удалённый.
Каталог релиза пустой до распаковки и после неё доступен только на чтение.

Раскладка на сервере:

```
/opt/drinkx-crm/
  incoming/<sha>.tar.gz     транзит, удаляется после распаковки
  releases/<sha>/           build context, ровно дерево коммита
  releases/.markers/<sha>   sha256 архива, из которого собрано это дерево
  current -> releases/<sha> переключается deploy.sh только после всех проверок
  shared/.env               секреты, вне любого дерева релиза
```

**Повторная подготовка того же SHA.** Раньше подготовка начиналась с
`rm -rf releases/<sha>`, а `current` после успешного деплоя указывает ровно
туда. Между удалением и переименованием ссылка `current` висела, а при
падении `mv` — оставалась висеть навсегда (REL-LOCAL-01).

Теперь `releases/<sha>` не трогается, если там уже лежит то же самое дерево.
`git archive` с `gzip -n` воспроизводим побайтно, поэтому повторная подготовка
приносит тот самый архив, из которого каталог и собран; sha256 архива лежит
в `releases/.markers/<sha>` и сверяется с входящим. Если маркера нет (дерево
готовили до этой проверки или руками) — содержимое сравнивается напрямую,
`diff -r`. Совпало — каталог переиспользуется как есть, `current` ни на
мгновение не перестаёт разрешаться.

Тот же SHA с другим содержимым `git archive` выдать не может. Если это всё же
случилось и `current` указывает на этот каталог, подготовка падает и ничего
не удаляет: заменить дерево работающего релиза значило бы снести точку
отката. Разбираться с этим — вручную.

Маркеры лежат в точечном каталоге рядом с деревьями, а не внутри них: build
context обязан быть ровно деревом коммита. Чистка старых релизов удаляет
маркер вместе с деревом и по-прежнему щадит и `current`, и только что
подготовленный SHA.

**Чего не удаляется.** Ничего за пределами `releases/` и `incoming/`. Глобального
`rsync --delete` по `/opt/drinkx-crm` нет намеренно: там же `.env`, логи и
состояние, принадлежащее серверу. Имя compose-проекта (`drinkx`) и тома
`drinkx_pg`, `drinkx_redis`, `drinkx_logs` не менялись — иначе поднялась бы
пустая база.

**Файл окружения.** `deploy.sh` ищет его по порядку: `$DRINKX_ENV_FILE`,
`<root>/shared/.env`, `<root>/infra/production/.env` (прежняя раскладка). Ручной
перенос на сервере не обязателен: пока старый путь существует, он и берётся.
Печатается, какой именно файл выбран.

**Второй слой.** Добавлены `.dockerignore` в корне и в `apps/web`. На проде
контекст и так чистый; это защита для сборки с чужой машины, где `COPY . .`
в web-образе забрал бы и `.env`, и `node_modules`.

**Что проверяется автоматически** —
`infra/production/tests/test_release_build_context.py`, job `release-gate`:

1. файл, удалённый между A и B, отсутствует в контексте B;
2. файл, добавленный в B, присутствует;
3. контекст равен `git ls-tree -r <sha>` — ни больше, ни меньше;
4. `.env` не попадает ни в архив, ни в контекст, и `shared/.env` цел;
5. untracked-файлы (и в чекауте CI, и на сервере) в контекст не попадают,
   при этом файл рядом в корне деплоя не удаляется;
6. испорченный архив — в четырёх видах, включая пересчитанную контрольную
   сумму, — не переключает работающий релиз и не публикует полудерево;
7. `deploy.sh` отказывает при сборке из накопительного каталога и не двигает
   `current` при провале сборки;
8. workflow не вернулся к `rsync` рабочего каталога.

Проверки прогонялись мутационно: четыре внесённых дефекта (лишний файл в
дереве, публикация полураспакованного дерева, снятый гейт в `deploy.sh`,
архив не того коммита) валят соответствующие пункты.

**Чего это по-прежнему не доказывает.** Что внутри собранного образа лежит
ровно это дерево. Образы здесь не собираются — за сборку отвечает
`check_image_identity.sh` в job `docker-smoke`, и она проверяет метки, а не
состав слоёв.

## 3. Порядок проверок перед выпуском

Обязательные проверки живут в одном переиспользуемом workflow `quality.yml`
и вызываются из двух точек входа:

- `pr.yml` — на каждый pull request;
- `deploy.yml` — на каждый кандидат выпуска, до самого выпуска.

Обязательных job пять: `api`, `migrations`, `web`, `release-gate`,
`docker-smoke`. Итоговый `quality-gate` ждёт всех пятерых и требует именно
`success`: `cancelled`, `skipped` и пропавший результат зелёными не считаются.
Job `deploy` зависит от гейта.

**Один коммит на весь прогон.** SHA определяется один раз в точке входа, каждый
job делает checkout именно его и сверяет `git rev-parse HEAD`. Схемы «проверили
A, выпустили текущий main B» нет. Ручной запуск разрешён только с `main` и гейт
не обходит. Секреты в `quality.yml` не передаются — код из pull request не
получает доступа к серверу.

**Path-фильтров нет намеренно.** Отфильтрованный workflow не выдаёт статус
вообще, а пропуски приходятся ровно на то, что здесь важно: `infra/production`,
сами workflow, оба Dockerfile, корневой lockfile и манифесты workspace. Полный
прогон медленнее и однозначен. Сужение — оптимизация на потом.

**Устаревший кандидат.** Деплои сериализованы и не отменяются на полпути.
Если пока прогон стоял в очереди, в `main` уехал более новый коммит, шаг
«Refuse a superseded candidate» останавливает выпуск с ошибкой. Выкатит тот
прогон, который соответствует новому коммиту. Красный прогон здесь означает
«этот кандидат не выпущен», а не «сломана сборка».

## 4. Безопасность тестовых баз

Фикстуры делают `DROP SCHEMA public CASCADE`, проверка миграций гоняет реальную
цепочку. Оба берут DSN из окружения, где чужая строка — одна ошибка.

`apps/api/scripts/db_safety.py` разбирает URL и проверяет по отдельности схему,
host, port и имя базы по списку разрешённых. Наличие слова «test» в имени
защитой не считается: `prod_latest_backup` его тоже содержит. Проверка идёт
**до** открытия соединения.

Форма DSN закрыта: query и fragment отклоняются. Читать URL самостоятельно и
надеяться, что драйвер прочтёт его так же, — это и подвело (замечание ревью R1):
строка `…/drinkx_test?host=elsewhere.invalid&database=not_disposable` проходила
проверку, а драйвер шёл на другой хост и в другую базу. Пароль может лежать и в
userinfo, и в `?password=`, поэтому `redact()` пересобирает строку по полям, а
не латает подстроку.

`REQUIRE_TEST_DB=1` в CI превращает недоступную базу или отсутствующий
async-драйвер в падение набора. Без этого тесты с базой просто пропускались и
набор отчитывался зелёным. Локально режим без базы по-прежнему допустим и явно
подписан в выводе. В конце прогона печатается, сколько тестов с базой реально
выполнено, а не только сколько собрано.

Базы для CI разные: `drinkx_test` для фикстур API, `drinkx_migrations_test` для
миграций. Общая база означала бы, что фикстуры сносят мигрированную схему.

## 5. Найденный дефект цепочки миграций

Новая проверка сразу упала на чистой базе:

```
value too long for type character varying(32)
UPDATE alembic_version SET version_num='0009_inbox_items_and_activity_email'
```

Alembic жёстко создаёт служебную колонку как `String(32)`
(`alembic/ddl/impl.py`, `version_table_impl`), опции для расширения нет.
Семь ревизий в проекте длиннее 32 символов, первая — `0009_…` на 35.

Значит, цепочка **не могла построить новое окружение**: восстановление после
аварии, новый стенд или очищенный том не поднялись бы, потому что контейнер API
выполняет `alembic upgrade head` до старта uvicorn.

Исправление не трогает историю миграций. Логика вынесена в
`apps/api/scripts/alembic_version_table.py` и сначала **смотрит** на колонку:

- таблицы нет — создаётся сразу нужной ширины;
- колонка уже достаточно широкая, `text` или без ограничения длины — DDL не
  выполняется вообще и ничего не сужается;
- колонка действительно узкая — один `ALTER`, и только он ограничен
  `SET LOCAL lock_timeout`, потому что смена типа берёт `ACCESS EXCLUSIVE` и без
  ограничения деплой мог бы ждать чужую транзакцию неограниченно.

Первая версия правки выполняла `CREATE IF NOT EXISTS` и `ALTER` при каждом
вызове (замечание ревью R3). Read-only команды (`current`, `heads`, `history`,
`show`, `branches`) bootstrap не выполняют совсем.

Отсутствие строк `Running upgrade` во втором прогоне само по себе **не**
доказывает, что повтор ничего не сделал: оно говорит лишь о том, что не
применялись файлы ревизий. `check_migrations.py` теперь отдельно проверяет, что
bootstrap во втором прогоне тоже промолчал.

> **Проверить на проде перед следующим выпуском.** Если боевая база сейчас на
> ревизии `0057`, а `0058_task_assignee_and_standalone` (33 символа) ещё не
> применена, то без этой правки следующий деплой упал бы на миграции. С правкой
> колонка расширяется автоматически при первом же запуске. Прод в этой работе
> не трогали, фактическую ширину колонки там никто не смотрел.

Побочное наблюдение: нумерация ревизий не соответствует порядку цепочки,
`…→ 0056 → 0058 → 0057 (head)`. Цепочка линейная и корректная, но head надо
брать у Alembic, а не из документа. Проверка так и делает.

## 6. Порядок безопасного применения

1. Открыть pull request. `pr.yml` прогонит все пять обязательных проверок на
   head-коммите ветки. **Docker собирается именно здесь** — merge в `main`
   остаётся выпуском, а не способом впервые проверить сборку.
2. Слить после зелёного гейта. Push в `main` запустит те же проверки на
   коммите слияния, затем `deploy`.
3. В шаге «Trigger deploy» ждать четыре строки `✓ <сервис> runs <sha>` и
   `DEPLOY_RESULT=success`, затем `✅ Production is serving <sha>`.

Первый прогон устойчив сам по себе. Если сборка падает, выполнение
заканчивается **до** проверки меток, и то, что на старых контейнерах метки нет,
первому успешному выпуску не мешает.

Жёсткие проверки API и web — задуманное fail-closed поведение. Деплой начнёт
падать там, где раньше проходил с предупреждением. Это и есть смысл правки,
возвращать предупреждение не нужно.

## 7. Откат

Автоматического отката нет намеренно: восстановление доступности и статус
выпуска — разные вещи, и неудачная попытка обязана оставаться неудачной.
Три разных отката, не путать:

- **Логика деплоя.** `git revert` коммитов G1/G2. Вернёт прежний скрипт вместе
  с прежним ложно-зелёным поведением. Контейнеры при этом сами не откатятся.
- **Приложение.** Выкатить предыдущий рабочий коммит через `main`. Общее
  состояние не трогается: тома `drinkx_pg`, `drinkx_redis`, `drinkx_logs` живут
  отдельно от образов, имя проекта compose (`drinkx`) не менялось.
- **Доставка (G4).** `git revert` коммита G4 вернёт `rsync` и прежний каталог
  `/opt/drinkx-crm/infra/production`, который на сервере никуда не делся —
  старый путь остался на диске нетронутым. Каталоги `releases/` при этом можно
  просто удалить. Хранится пять последних релизов, так что откат на предыдущее
  дерево — это `DEPLOY_SHA=<старый> bash /opt/drinkx-crm/releases/<старый>/infra/production/deploy.sh`,
  без обращения к GitHub. Повторная подготовка того же SHA каталог отката не
  сносит: дерево, на которое смотрит `current`, подготовка не удаляет никогда.
  Если каталоги `releases/` удаляются вручную, удалите вместе с ними и
  `releases/.markers/` — иначе маркер переживёт дерево, и следующая подготовка
  этого SHA сверится с несуществующим каталогом (это безопасно: сверка идёт
  только когда каталог есть, но мусор ни к чему).
- **Схема БД.** Автоматического `alembic downgrade` нет и не добавлялось.
  Откат схемы планируется отдельно под конкретную миграцию.

## 8. Как прогнать проверки локально

```bash
python3 infra/production/tests/test_deploy_release_gate.py
python3 infra/production/tests/test_release_pipeline_wiring.py
python3 infra/production/tests/test_release_build_context.py
python3 infra/production/tests/repro_build_context_debt01.py
```

Первая гоняет настоящий `deploy.sh` с заглушками `docker`, `curl` и `sleep`:
