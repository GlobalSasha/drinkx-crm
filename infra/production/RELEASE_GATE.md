# Релизный гейт (аудит G1 + G2)

Что проверяется перед выпуском, как это применить и как откатить.
Код изменён локально. На production ничего не применялось, ни один workflow
на GitHub не запускался.

## 1. Что было сломано

**G1 / BUG-01.** `deploy.sh` собирал и запускал контейнеры одной командой
`up -d --build || UP_RC=$?`. Ненулевой код сборки только печатал предупреждение.
Дальше шли health-проверки, на которые исправно отвечал предыдущий релиз,
и скрипт завершался нулём. Оператор видел зелёный деплой без новой версии.

Попутно: исчерпанный бюджет ожидания API не считался провалом, а недоступность
web была предупреждением.

**G1 acceptance.** Первая версия исправления сверяла версию через
`printenv DRINKX_GIT_SHA` внутри контейнера. Это не доказательство: `ENV` образа
переопределяется при запуске, поэтому старый образ, поднятый с переменной нового
релиза, проходил проверку.

**G2 / DEBT-02.** Деплой висел на собственном событии push и ни от чего не
зависел. Проверки API и web жили в отдельных workflow со своими path-фильтрами,
так что правка в `infra/`, в workflow или в корневом lockfile уезжала в прод,
не будучи проверенной ничем.

**G2 / DEBT-03.** Тестовые фикстуры строят схему через `metadata.create_all`,
а прод поднимается через `alembic upgrade head`. Два разных пути, покрыт был
один. Новая проверка миграций сразу нашла настоящий дефект — см. раздел 5.

## 2. Чем доказывается версия

`GIT_SHA` приходит build-аргументом и попадает в образ двумя способами:

| Место | Для чего | Можно ли подделать в рантайме |
|---|---|---|
| `ENV DRINKX_GIT_SHA` | удобство внутри приложения, поле `sha` в `/health` | **да**, через `docker run -e` |
| `LABEL org.opencontainers.image.revision` | решение гейта | нет, метка принадлежит образу |

Поэтому гейт читает **метку образа**, а не окружение контейнера. Порядок такой:

1. после сборки запоминаются ID собранных образов и проверяется, что их метки
   называют нужный коммит;
2. после запуска для каждого из четырёх сервисов берётся ID образа, с которого
   реально поднят контейнер, и сверяется с запомненным;
3. из образа по этому ID читается метка и сверяется с `DEPLOY_SHA`.

`/health` и `/version` отдают `sha` и остаются проверкой того, что API
действительно обслуживает запросы. Они **не** заменяют проверку образов:
поле берётся из окружения, а его можно подменить.

Последняя строка скрипта всегда одна из трёх:

| Строка | Значение |
|---|---|
| `DEPLOY_RESULT=success` | все четыре контейнера подняты с образов этой сборки |
| `DEPLOY_RESULT=unverified` | запуск вручную без `DEPLOY_SHA`, сверять не с чем |
| `DEPLOY_RESULT=failed` | сборка, запуск, health или идентичность не прошли |

**Чего это не доказывает.** Что образ собран из чистого дерева этого коммита.
Rsync на сервер идёт без `--delete`, поэтому удалённый из git файл может дожить
до сборки. Это отдельная задача G4. Совпадение метки говорит «собрано с таким
`GIT_SHA`», а не «собрано ровно из этого дерева».

## 3. Порядок проверок перед выпуском

Обязательные проверки живут в одном переиспользуемом workflow `quality.yml`
и вызываются из двух точек входа:

- `pr.yml` — на каждый pull request;
- `deploy.yml` — на каждый кандидат выпуска, до самого выпуска.

Обязательных job пять: `api`, `migrations`, `web`, `release-gate`,
`docker-smoke`. Итоговый `quality-gate` ждёт всех пятерых и требует именно
`success`: `cancelled`, `skipped` и пропавший результат зелёными не считаются.
Job `deploy` зависит от гейта.

**Один коммит на весь прогон.** SHA определяется один раз в точке входа, каждый
job делает checkout именно его и сверяет `git rev-parse HEAD`. Схемы «проверили
A, выпустили текущий main B» нет. Ручной запуск разрешён только с `main` и гейт
не обходит. Секреты в `quality.yml` не передаются — код из pull request не
получает доступа к серверу.

**Path-фильтров нет намеренно.** Отфильтрованный workflow не выдаёт статус
вообще, а пропуски приходятся ровно на то, что здесь важно: `infra/production`,
сами workflow, оба Dockerfile, корневой lockfile и манифесты workspace. Полный
прогон медленнее и однозначен. Сужение — оптимизация на потом.

**Устаревший кандидат.** Деплои сериализованы и не отменяются на полпути.
Если пока прогон стоял в очереди, в `main` уехал более новый коммит, шаг
«Refuse a superseded candidate» останавливает выпуск с ошибкой. Выкатит тот
прогон, который соответствует новому коммиту. Красный прогон здесь означает
«этот кандидат не выпущен», а не «сломана сборка».

## 4. Безопасность тестовых баз

Фикстуры делают `DROP SCHEMA public CASCADE`, проверка миграций гоняет реальную
цепочку. Оба берут DSN из окружения, где чужая строка — одна ошибка.

`apps/api/scripts/db_safety.py` разбирает URL и проверяет по отдельности схему,
host, port и имя базы по списку разрешённых. Наличие слова «test» в имени
защитой не считается: `prod_latest_backup` его тоже содержит. Пароль в
сообщениях об ошибке вырезается. Проверка идёт **до** открытия соединения.

`REQUIRE_TEST_DB=1` в CI превращает недоступную базу или отсутствующий
async-драйвер в падение набора. Без этого тесты с базой просто пропускались и
набор отчитывался зелёным. Локально режим без базы по-прежнему допустим и явно
подписан в выводе. В конце прогона печатается, сколько тестов с базой реально
выполнено, а не только сколько собрано.

Базы для CI разные: `drinkx_test` для фикстур API, `drinkx_migrations_test` для
миграций. Общая база означала бы, что фикстуры сносят мигрированную схему.

## 5. Найденный дефект цепочки миграций

Новая проверка сразу упала на чистой базе:

```
value too long for type character varying(32)
UPDATE alembic_version SET version_num='0009_inbox_items_and_activity_email'
```

Alembic жёстко создаёт служебную колонку как `String(32)`
(`alembic/ddl/impl.py`, `version_table_impl`), опции для расширения нет.
Семь ревизий в проекте длиннее 32 символов, первая — `0009_…` на 35.

Значит, цепочка **не могла построить новое окружение**: восстановление после
аварии, новый стенд или очищенный том не поднялись бы, потому что контейнер API
выполняет `alembic upgrade head` до старта uvicorn.

Исправление минимальное и не трогает историю: `alembic/env.py` перед запуском
цепочки создаёт служебную таблицу нужной ширины, а существующую расширяет.
Операция идемпотентная, таблица из одной строки. Альтернатива — переименовать
семь исторических ревизий, на которые уже ссылаются живые базы.

> **Проверить на проде перед следующим выпуском.** Если боевая база сейчас на
> ревизии `0057`, а `0058_task_assignee_and_standalone` (33 символа) ещё не
> применена, то без этой правки следующий деплой упал бы на миграции. С правкой
> колонка расширяется автоматически при первом же запуске. Прод в этой работе
> не трогали, фактическую ширину колонки там никто не смотрел.

Побочное наблюдение: нумерация ревизий не соответствует порядку цепочки,
`…→ 0056 → 0058 → 0057 (head)`. Цепочка линейная и корректная, но head надо
брать у Alembic, а не из документа. Проверка так и делает.

## 6. Порядок безопасного применения

1. Открыть pull request. `pr.yml` прогонит все пять обязательных проверок на
   head-коммите ветки. **Docker собирается именно здесь** — merge в `main`
   остаётся выпуском, а не способом впервые проверить сборку.
2. Слить после зелёного гейта. Push в `main` запустит те же проверки на
   коммите слияния, затем `deploy`.
3. В шаге «Trigger deploy» ждать четыре строки `✓ <сервис> runs <sha>` и
   `DEPLOY_RESULT=success`, затем `✅ Production is serving <sha>`.

Первый прогон устойчив сам по себе. Если сборка падает, выполнение
заканчивается **до** проверки меток, и то, что на старых контейнерах метки нет,
первому успешному выпуску не мешает.

Жёсткие проверки API и web — задуманное fail-closed поведение. Деплой начнёт
падать там, где раньше проходил с предупреждением. Это и есть смысл правки,
возвращать предупреждение не нужно.

## 7. Откат

Автоматического отката нет намеренно: восстановление доступности и статус
выпуска — разные вещи, и неудачная попытка обязана оставаться неудачной.
Три разных отката, не путать:

- **Логика деплоя.** `git revert` коммитов G1/G2. Вернёт прежний скрипт вместе
  с прежним ложно-зелёным поведением. Контейнеры при этом сами не откатятся.
- **Приложение.** Выкатить предыдущий рабочий коммит через `main`. Общее
  состояние не трогается: тома `drinkx_pg`, `drinkx_redis`, `drinkx_logs` живут
  отдельно от образов, имя проекта compose (`drinkx`) не менялось.
- **Схема БД.** Автоматического `alembic downgrade` нет и не добавлялось.
  Откат схемы планируется отдельно под конкретную миграцию.

## 8. Как прогнать проверки локально

```bash
python3 infra/production/tests/test_deploy_release_gate.py
python3 infra/production/tests/test_release_pipeline_wiring.py
```

Первая гоняет настоящий `deploy.sh` с заглушками `docker`, `curl` и `sleep`:
ни демона Docker, ни SSH, ни сети, ни production. Вторая читает workflow и
проверяет граф выпуска. Структурная проверка не доказывает поведение прогона
на GitHub — это разные вещи.

```bash
cd apps/api
REQUIRE_TEST_DB=1 uv run pytest -q
DATABASE_URL=postgresql+asyncpg://drinkx:dev@localhost:5432/drinkx_migrations_test \
  uv run python scripts/check_migrations.py
```

Проверка миграций требует отдельной одноразовой базы. Страж DSN откажется
работать с чем-либо, кроме разрешённого списка.
