# Релизный гейт деплоя (аудит G1 / BUG-01)

Что изменилось, как это применить на сервере и как откатить.
Код изменён локально; на production ничего не применялось.

## Зачем

До этой правки `deploy.sh` собирал и запускал контейнеры одной командой
`up -d --build || UP_RC=$?`. Ненулевой код сборки только печатал предупреждение.
Дальше шли health-проверки, на которые исправно отвечал **предыдущий** релиз,
и скрипт завершался нулём. Оператор видел зелёный деплой, хотя новая версия
на сервер не попадала.

Дыр было три:

1. Ошибка сборки не прерывала выпуск.
2. Никто не сверял, какая версия реально запущена.
3. Исчерпанный бюджет health-проверок API не считался провалом, а недоступность
   web была всего лишь предупреждением.

## Как теперь доказывается версия

`GIT_SHA` приходит build-аргументом и запекается в образ как `DRINKX_GIT_SHA`
(`apps/api/Dockerfile`, `apps/web/Dockerfile`). Переменной нет в секции
`environment:` compose — и это принципиально: рантайм-переменную можно
подсунуть старому образу, а метку внутри образа подделать нельзя, не пересобрав его.

Проверяют версию дважды:

- `deploy.sh` на сервере читает `printenv DRINKX_GIT_SHA` в каждом из четырёх
  контейнеров (`api`, `web`, `worker`, `beat`) и сверяет с `DEPLOY_SHA`;
- workflow снаружи читает поле `sha` из `GET /api/health` и сверяет с `github.sha`.

Последняя строка скрипта всегда одна из трёх:

| Строка | Значение |
|---|---|
| `DEPLOY_RESULT=success` | все четыре контейнера запущены из ожидаемого коммита |
| `DEPLOY_RESULT=unverified` | запуск вручную без `DEPLOY_SHA`, проверить версию нечем |
| `DEPLOY_RESULT=failed` | сборка, запуск, health или версия не прошли; выход ненулевой |

## Порядок безопасного применения

1. Слить ветку в `main` обычным PR. Первый же автодеплой пересоберёт образы
   и впервые запечатает в них метку версии.
2. Смотреть шаг «Trigger deploy» в Actions. На здоровом выпуске в логе будут
   четыре строки `✓ <сервис> runs <sha>` и `DEPLOY_RESULT=success`.
3. Следом шаг «Verify running version» должен напечатать `✅ Production is serving <sha>`.

Первый прогон устойчив сам по себе: метку читают уже из пересобранных образов.
Если сборка упадёт, старые контейнеры метки не имеют, `printenv` вернёт пусто,
и деплой честно завершится ошибкой вместо ложного успеха.

Проверка на staging этой правкой **не выполнялась**. Если нужен прогон без риска
для боевого стенда — поднять копию стека на тестовом хосте и прогнать деплой
дважды: с заведомо сломанной сборкой и с рабочей.

## Откат

Автоматического отката в скрипте нет намеренно: восстановление доступности и
статус выпуска — разные вещи, и неудачная попытка обязана оставаться неудачной.

- **Откатить поведение деплоя.** `git revert` коммита G1 и обычный деплой.
  Вернётся прежний скрипт, включая прежнее ложно-зелёное поведение.
- **Откатить приложение.** Выкатить предыдущий рабочий коммит через `main`.
  Общее состояние не трогается: тома `drinkx_pg`, `drinkx_redis` и `drinkx_logs`
  живут отдельно от образов, имя проекта compose (`drinkx`) не менялось.
- **Миграции БД.** Автоматического `alembic downgrade` нет и не добавлялось.
  Откат схемы планируется отдельно под конкретную миграцию.


на `PATH`. Ни демона Docker, ни SSH, ни сети, ни production. Семь сценариев плюс
статическая проверка, что метка версии остаётся build-time и не просочилась
в `environment:`.
