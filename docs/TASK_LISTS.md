# Списки задач: контракт и постраничная выдача (аудит G5)

Что было сломано, что стало, и на что смотреть при правках.
Код изменён локально. На production ничего не применялось, ни один workflow
на GitHub не запускался.

## 1. Что было сломано

Общая суть обоих дефектов одна: **актуальная задача исчезала из интерфейса
только потому, что перед ней оказалось много других записей.**

**A. Карточка лида.** Вкладка «Задачи» брала
`GET /leads/{id}/activities?type=task&limit=200`. Лента упорядочена по времени
события (`created_at DESC`), ответ содержит `next_cursor` — и фронтенд его
выбрасывал. На лиде с историей длиннее двухсот записей открытая задача,
заведённая раньше остальных, оказывалась на второй странице, за которой никто
не ходил.

Воспроизведение: 251 задача на лиде, единственная открытая — самая старая.
Ответ: 200 строк, все закрытые, `next_cursor` есть, открытой задачи нет.
Плюс клиентская часть: один запрос, ни одного обращения с курсором.

**B. `/me/tasks`.** Запрос сортировался по сроку, **не фильтровал по статусу
вообще** и обрывался на `limit(500)`. Пятьсот закрытых задач с более ранними
сроками занимали весь бюджет.

Воспроизведение: 500 закрытых задач с прошедшими сроками плюс одна открытая
с будущим. Ответ: 500 строк, все закрытые, открытой нет.

Логи обоих прогонов до правки лежат в review-пакете G5. Сами сценарии —
`apps/api/tests/repro_g5_defects.py` (файл намеренно не подхватывается
pytest: он утверждает поведение ДО правки, а не после).

## 2. Один порядок для всех списков задач

```
task_done ASC, task_due_at ASC NULLS LAST, id DESC
```

Применяется в базе, до любого среза.

**`task_done` первым** — это и есть исправление дефекта B. Пока сортировка
начиналась со срока, закрытая задача с ранним дедлайном шла впереди открытой
с поздним, и при любом лимите список заполнялся историей.

**`id DESC`** — не украшение. Одинаковый `task_due_at` встречается постоянно:
пачка задач от одной автоматизации, круглый час, набранный руками. Keyset-курсор
по неуникальному ключу на каждой границе страницы либо пропускает строки, либо
повторяет их. Идентификатор делает порядок полным.

**NULLS LAST** — задачи без срока уходят в конец, но остаются достижимыми
перелистыванием.

## 3. Почему курсор, а не `page/page_size`

В проекте есть оба стиля: лиды листаются `page/page_size` с `total`, лента
активностей — курсором. Для задач выбран курсор, и вот почему.

Список задач отсортирован ровно по тем двум колонкам, которые пользователь
меняет прямо во время чтения. Отметил галочку — строка переехала из начала
списка в конец. При `OFFSET` соседняя строка сдвигается через границу страницы
и не показывается вообще: ровно тот класс пропаж, ради которого эта работа и
делалась. Keyset от такого не страдает: следующая страница определяется
значением ключа, а не номером.

То, ради чего обычно держат `total`, отдаётся отдельно — см. счётчики.

## 4. Контракт ответа

Три эндпоинта отвечают одинаково:

| Эндпоинт | Что показывает |
|---|---|
| `GET /tasks` | страница «Задачи»: руководитель и админ видят команду, менеджер — свои и поставленные им |
| `GET /me/tasks` | задачи, которые числятся за этим человеком (виджет «Сегодня», напоминания) |
| `GET /leads/{id}/tasks` | все задачи одного лида — вкладка в карточке |

```jsonc
{
  "items": [ /* MyTaskOut */ ],
  "next_cursor": "0|2026-09-20T10:00:00+00:00|9f1c…",  // null на последней странице
  "counts": { "total": 251, "open": 1, "done": 250, "overdue": 0 }
}
```

Параметры: `status` (`all|open|done|overdue`), `cursor`, `limit`
(потолок — 200; у `/me/tasks` по умолчанию 100, у остальных 50).

**Курсор непрозрачен.** Это полный ключ сортировки последней строки. Клиент
возвращает его как есть; разбирать его на клиенте не нужно и не следует.
Курсор не из этого эндпоинта — `400`, а не молчаливая первая страница.

**Это ломающее изменение.** Раньше все три отдавали голый массив. Обновлены
все потребители: `useTasks`, `useMyTasks`, `useLeadTasks`, страница «Задачи»,
виджет «Сегодня», напоминания, вкладка карточки лида и типы в `lib/types.ts`.
Внешнее API (`/external/v1`, MCP) задач не отдаёт — проверено.

## 5. Счётчики

`counts` считаются по **всей серверной выборке** и **до** фильтра по статусу:
фильтры по исполнителю, автору и лиду учитываются, статус — нет. Поэтому чип
«закрытые» знает свой размер, пока выбран чип «открытые».

Так сделано потому, что интерфейс показывает эти числа как факты о работе
человека: прогресс «N из M выполнено» в виджете «Сегодня», «показано X из Y»
под списками, выбор между «Задач нет» и «Ничего не найдено» в пустом
состоянии. Считать их по загруженной странице — значит показывать размер
страницы вместо размера работы.

## 6. Что осталось клиентским и почему это видно

Поиск по тексту и фильтр по сроку (сегодня / неделя) применяются к уже
загруженным страницам. Под списком об этом написано прямо: «поиск и срок
применяются к загруженным». Уносить их на сервер — отдельная работа
(нужен полнотекстовый индекс по тексту задачи), а молчаливый частичный поиск
— это тот же дефект, что чинили.

Вкладка карточки лида и страница «Задачи» историю сами не тянут: первая
страница, дальше «Показать ещё». Виджет «Сегодня» держит одну страницу и,
когда задач больше, говорит «Показаны первые N из M» со ссылкой на полный
список.

## 7. Что специально не изменилось

- **Лестница исполнителя:** явный → владелец лида → автор. Рядом появилось
  поле `explicit_assignee_user_id` — значение из самой строки, до применения
  лестницы. Оно нужно селектору «Поручить»: пустой выбор там означает
  «делает владелец лида», и подстановка вычисленного владельца превратила бы
  неявное назначение в явное при первом сохранении.
- **Права (G3):** менеджер не видит задач коллеги; руководитель и админ видят
  команду и фильтруют по исполнителю. Проверено на постраничном запросе, в том
  числе по счётчикам — они тоже не должны выдавать чужой объём.
- **Вкладка карточки** показывает работу по лиду целиком, а не только задачи
  читателя. Это её поведение до G5, и оно сохранено: `GET /leads/{id}/tasks`
  не сужается до актора.

  Но открыть саму карточку надо иметь право, и правило то же, что у `/leads`:
  руководитель и админ — любой лид своего пространства, менеджер — только
  закреплённый за ним; чужой лид и лид другого пространства одинаково дают
  404, включая счётчики. Проверку делает `lead_access_guard`
  (`app/leads/access.py`) — один страж на оба роутера. В первой версии G5
  эндпоинт был подключён отдельным роутером, страж `/leads` на него не
  распространялся, а сервис сверял только рабочее пространство: менеджер,
  знающий UUID, читал задачи чужого лида. Регрессии —
  `apps/api/tests/test_lead_tasks_access.py`, через HTTP, потому что правило
  живёт в зависимости роутера и вызовом обработчика не проверяется.
- **`GET /leads/{id}/activities?type=task`** — порядок и курсор не тронуты.
  Это лента событий со своим, хронологическим порядком; задачи из неё больше
  никто не берёт. Доступ у неё теперь такой же, как у карточки: тот же
  `lead_access_guard` подключён и к роутеру ленты — он висел отдельно от
  `/leads` и имел ровно ту же дыру, причём не только на чтение (по тем же
  маршрутам чужую ленту можно было пополнять, а чужие задачи закрывать и
  удалять). Регрессии — `apps/api/tests/test_lead_activities_access.py`.

## 8. Регрессии

`apps/api/tests/test_task_list_completeness.py` — 14 проверок:

- открытая задача старше двухсот других на первой странице лида;
- открытая задача после пятисот закрытых в `/me/tasks`;
- перелистывание лида отдаёт каждую задачу ровно один раз;
- одинаковый `task_due_at` при размерах страницы 1, 2, 7 и 10;
- `task_due_at = null` — в конце и достижима;
- открытые и закрытые не перемешиваются между страницами;
- `open` / `done` / `overdue` отбираются в базе, в том числе при `limit=1`;
- счётчики не сжимаются до страницы и не меняются при выборе статуса;
- чужой курсор отвергается;
- задача без лида;
- явный исполнитель, откат на владельца, откат на автора;
- менеджер не получает задач коллеги — ни строками, ни счётчиком;
- страница ограничена потолком, а не «просто большим числом».

Фронтенд: `apps/web/lib/hooks/use-lead-tasks.test.tsx` (4) и
`use-tasks-pagination.test.tsx` (4) — запрос к новому эндпоинту, загрузка
следующей страницы по курсору, счётчики по всей выборке, отправка статуса на
сервер и перечитывание **всех** загруженных страниц после мутации.
