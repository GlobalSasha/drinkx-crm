## 1. Как CRM реально устроена сейчас

### Что известно по прочитанному коду и документам базы аудита

- Монорепозиторий: `apps/web` — Next.js 15 / React 19 / TypeScript, `apps/api` — FastAPI / SQLAlchemy async / Pydantic; конфигурация и скрипты — `infra`.
- Frontend использует TanStack Query для серверных данных, Zustand для клиентского состояния, Tailwind / компоненты на базе shadcn/ui. Значимая часть найденных багов находится на границе API и клиентского кэша.
- Backend организован по предметным областям. Для текущего аудита существенно изучены `activity`, `leads`, части `scheduled`, тестов и инфраструктуры; это не полный обход всех доменов.
- Задача представлена строкой `Activity(type=task)`. Есть lead-scoped endpoints и отдельный `/tasks`; возможны задачи без лида и явный исполнитель. Именно параллельные пути требуют согласованного контракта.
- Есть роли `admin`, `head`, `manager`. Наличие ролей не доказывает корректность всех проверок доступа — это направление 4.
- Фоновые задачи используют Celery и Redis. Хранилище данных — PostgreSQL; Supabase используется в auth/integration-конфигурации. Фактическое размещение production-БД не подтверждено доступом к окружению и требует сверки, поскольку документы расходятся.
- Отслеживаемый production-контур — Docker Compose на сервере, web/api/worker/beat; GitHub Actions. В базе аудита любой push в `main` запускает deploy. Старое упоминание Vercel/Railway в README не принимать за текущую схему.
- AI- и почтовые интеграции присутствуют; активную модель, параметры, стоимость и рабочий статус каждой интеграции отдельно не верифицировали.

### Следующий результат направления 1

- [ ] Составить карту реальных маршрутов, доменов и владельцев данных по актуальному commit.
- [ ] Проследить пути: лид → назначение → задача → действие → уведомление; входящее сообщение → привязка; AI job → результат; экспорт → файл.
- [ ] Сверить Compose, startup, миграции, worker/beat и CI с документацией. Не выдавать конфигурацию Git за проверенное состояние production.
- [ ] Привязать каждый элемент карты к исходникам; устранить только подтверждённые противоречия документов.

### Текущая приёмка G1/G2: R1–R3

**R1 — P1, тестовая БД.** `apps/api/scripts/db_safety.py` из review-пакета проверяет основную часть DSN, но не переопределения адреса/БД/порта в query. Реальный разбор SQLAlchemy показал несовпадение разрешённой цели и цели драйвера, без открытия соединения. `redact()` также не скрывает пароль в query.

- [ ] Сделать закрытый контракт DSN: для минимального решения отклонять неподдерживаемые query/fragment до подключения. Если поддерживать параметры — проверять конечную цель после всех переопределений.
- [ ] Не выводить секреты из userinfo/query в диагностике.
- [ ] Постоянные тесты: host/database/port override, повторные и закодированные параметры, fragment, неподдерживаемые формы. Отказ должен происходить до подключения/Alembic/DDL.
- [ ] Сохранить fail-fast при недоступной обязательной тестовой БД; подключить регрессии к quality.

**R2 — P1, выбор образа сервиса.** `deploy.sh` и `infra/production/tests/check_image_identity.sh` используют первую строку `config --images`. В рассмотренной реализации Compose список может включать зависимости. Изолированная модель воспроизвела ложные отказы исправного выпуска. Реальная версия Compose production не измерялась.

- [ ] Однозначно разрешать service → image; не выбирать по позиции в списке.
- [ ] Исправить и release-скрипт, и Docker smoke.
- [ ] Ожидаемые image ID получать после build, ДО запуска. Не определять ожидание через уже работающий контейнер.
- [ ] Заглушки: API и web имеют разные image ID даже при одном revision. Покрыть зависимости и многострочный вывод.
- [ ] Сохранить отказ для старого образа A с runtime SHA B; окружение процесса не является доказательством образа.

**R3 — P2, изменение служебной таблицы Alembic.** В проверенном `env.py` helper безусловно выдаёт `ALTER ... TYPE VARCHAR(255)` при online-вызовах, в том числе повторно и при чтении `current`. Результат на регистрирующем соединении подтверждён; реальные production-блокировки не измерялись.

- [ ] Создавать широкую таблицу при отсутствии, расширять существующую только при необходимости.
- [ ] Не сужать достаточный тип; не повторять ALTER на уже корректной колонке.
- [ ] Ограничить ожидание блокировки служебной операции; сохранить корректные транзакционные границы.
- [ ] Read-only `alembic current` не должен скрыто выполнять bootstrap DDL.
- [ ] Автоматические проверки на одноразовой БД: пустая схема; существующая узкая таблица; сохранение ревизии и контрольных прикладных данных; уже достаточный тип; ограниченный отказ при блокировке.

Исправлять новыми точечными commits поверх проверенного G2, не переписывать G1/G2 с нуля. Не расширять R1–R3 до registry, подписей образов, нового стека или G4.

## 4. Security-риски

**Полный security-аудит не проведён.** R1 — подтверждённый риск в локально предложенном тестовом tooling, не обнаруженная эксплуатация production. Не объявлять остальные пункты уязвимостями до проверки.

- [ ] Авторизация: workspace isolation, права manager/head/admin на все lead-scoped и task-scoped пути, файлы, поиск, экспорт, задачи без лида. Проверять прямые API-запросы, не только скрытые кнопки.
- [ ] Auth: приглашения, callback, session lifecycle, отозванные пользователи и смена ролей.
- [ ] Секреты: хранение/шифрование интеграционных credentials, логирование, client bundle, CI-права. Настоящие значения не публиковать в отчёте.
- [ ] Входящие данные и внешние вызовы: формы, загрузки, email/webhook, web-fetch/SSRF, лимиты, валидация, replay/idempotency.
- [ ] AI: недоверенный контент, доступные действия, подтверждение человеком, scope инструментов; не предоставлять сырой SQL.
- [ ] Supply chain / release: зависимости, permissions, branch protection/rulesets, доступ к production. Проверять актуальные настройки, не опираться на старый снимок.

Выход: конкретный finding → путь/сценарий → условия эксплуатации → подтверждение → приоритет → минимальное исправление. Проверки без реальных секретов, удалений или обращения к production без разрешения.

## 5. Архитектурные проблемы

Подтверждённая исходная тема — несколько путей записи/чтения одной задачи с различающимися контрактами и кэшами; это исправляется в G3/G5. Полный архитектурный вердикт ещё не сформирован.

- [ ] Сопоставить домены и зависимости; отметить реальные циклы и дублирование бизнес-правил, а не просто большие файлы.
- [ ] Проверить границы транзакций: сохранение сущности, уведомления, очередь, retries и частичные ошибки.
- [ ] Проверить фоновые задачи: повторный запуск, идемпотентность, восстановление, таймауты, observability.
- [ ] Проверить согласованность контрактов API, схем, pagination, frontend types и null/omitted semantics.
- [ ] Измерить горячие SQL/N+1 и объём данных на реалистичных тестовых наборах; не назначать оптимизацию только по впечатлению.
- [ ] Описать необходимые изменения малыми шагами с совместимостью и критериями приёмки. Не превращать аудит в переписывание монорепозитория.

## 6. Frontend/UX проблемы

Часть сквозных дефектов уже зафиксирована: сброс исполнителя, срок задачи, обработка ошибок, устаревший кэш, неполный поиск, несоответствие экспорта. Общий визуальный/UX-аудит не выполнен; старые UX-заметки требуется перепроверить.

- [ ] Задачи: создание, делегирование, возврат владельцу, закрытие/переоткрытие, архив/восстановление, задачи без лида; сравнить карточку лида, «Задачи», «Сегодня».
- [ ] Лиды: пул → выдача → карточка → воронка; поиск, фильтры, pagination и массовые действия должны описывать одну выборку.
- [ ] Состояния: initial/loading/empty/error/retry/pending/success; при ошибке не терять ввод и не имитировать сохранение.
- [ ] Навигация по ролям, клавиатура, focus, доступность, мобильные сценарии. Не объявлять недоступность доказанной без проверки.
- [ ] Проверить производительность отображения и согласованность дизайн-системы после функциональной стабилизации.

Выход: воспроизводимые пользовательские сценарии и критерии приёмки; для визуальных выводов нужны фактические экраны, не только исходники.

Предварительный вывод по имеющейся разведке: важнее надёжность изменений и достоверность данных, чем косметический рефакторинг.

## 8. Приоритетный план P0 / P1 / P2

**P0:** подтверждённая критическая ситуация, требующая немедленного ограничения риска. В этом аудите подтверждённых production-инцидентов P0 не установлено; это не гарантия их отсутствия.  
**P1:** надёжность выпуска, безопасность разрушительных тестов, корректность работы с задачами и выборками.  
**P2:** устойчивость, согласованность UI/кэша, сопровождение. R3 остаётся условием приёмки изменяемого startup, несмотря на P2.

### Границы следующих блоков

**G3:** различать отсутствующее поле, `null` и значение; сохранить серверные права делегирования. Срок оставить необязательным согласно принятому в спеках контракту `/tasks`. Ошибки показывать, форму не очищать при неуспехе. Общая invalidation должна охватывать tasks/my-tasks/lead tasks/feed/today по смыслу; проверить с настоящим QueryClient. Realtime между разными пользователями не добавлять автоматически.

**G4:** не добавлять слепо `rsync --delete` на весь production-каталог. Не менять имя проекта Compose и не удалять тома. Выпуск должен строиться из определённого чистого дерева; revision label — не замена этой гарантии.

**G5:** серверные фильтры и сортировка до ограничения, продолжение списка и согласованные totals. Не решать увеличением лимита до 5000. Отдельно проверить 500 завершённых старых задач + одну открытую с будущим сроком.

**G6:** сохранить существующую семантику фильтров, в том числе множественный выбор и AND по выбранным тегам; не потерять form/needs_review. Общий серверный predicate для list/count/export/выдачи, права и защита от гонок назначения. Не применять локальный фильтр только к одной странице.

## Правило закрытия и обновления плана

Для каждого блока вести раздельно: **реализация → review → release evidence → выпуск**. Commit, пройденные mocks или фраза «готово» не закрывают автоматически все четыре состояния. Закрытие всех G-этапов первого пакета также не означает завершения восьми направлений аудита.

В конце каждой выполненной задачи обновлять этот же файл, а не создавать новый конкурирующий мастер-план:

```text
Дата:
Направление / этап / finding ID:
Проверенный base и HEAD:
Ветка, commit, PR (если существует):
Что изменено и что принято:
Проверки: команда → результат → источник лога:
NOT RUN и причины:
Открытые замечания:
Следующее конкретное действие:
Что требует отдельного разрешения владельца:
```

Только факты: не отмечать успешным непроведённый тест; не объявлять release, если был лишь локальный commit. Исполнитель сначала сверяет новый код — уже устранённые дефекты повторно не переделывать. Идентификаторы BUG/DEBT/G/R сохранять.

После публикации читать ветку `docs/crm-audit-master-plan`, пока файл явно не перенесён в `main`. Отсутствие файла в `main` до такого переноса ожидаемо. При переносе сохранить этот путь и обновить указание канонической ветки.
